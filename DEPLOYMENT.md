# Deploying SMARTLAB

Two shapes are possible, and they are not interchangeable. Read the
constraint first, because it decides which one you want.

---

## The constraint: Wake-on-LAN

Admin → Monitoring can power a laboratory PC **on**. It does that by
broadcasting a Wake-on-LAN magic packet, and a broadcast does not cross a
router. That is a property of the protocol, not of this code.

So the server must sit **on the same network as the laboratory PCs** for
"Power on" to work. Everything else — shut down, restart, lock, messages,
screenshots, bookings, the kiosk — works either way, because the agents
poll outward and do not need to be reachable.

| Feature | On-premises | Cloud |
| --- | --- | --- |
| Bookings, users, reports | works | works |
| Kiosk check-in and printing | works | works |
| Agent heartbeats, screens | works | needs internet in the lab |
| Shut down / restart / lock | works | works |
| **Power on (Wake-on-LAN)** | **works** | **does not work** |
| Real HTTPS certificate | needs setting up | included |
| Reachable off campus | no | yes |

## Option A — On-premises (recommended for the laboratory)

One machine in the laboratory runs the API and serves the app. Everything
works, including Wake-on-LAN, and the laboratory keeps running when the
internet does not.

### 1. Prepare the machine

Give it a **static IP** (or a DHCP reservation) — agents, the kiosk and
every bookmark point at that address. Say `192.168.1.50`.

Install Node 20 or newer.

### 2. Configure

`backend/.env`:

```ini
NODE_ENV=production
PORT=5000
CORS_ORIGIN=https://192.168.1.50:5000
SUPABASE_URL=https://<your-project>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service role key>
JWT_SECRET=<64+ random characters>
AGENT_API_KEY=<random>
KIOSK_API_KEY=<random, different from AGENT_API_KEY>
ADMIN_SIGNUP_CODE=<random, or empty to disable admin self-registration>
LAB_TIMEZONE=Asia/Manila
USE_HTTPS=true
```

Generate each secret with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

`frontend/.env` — **leave `VITE_KIOSK_KEY` unset**. See Security below.

### 3. Certificate

The kiosk camera only works on a secure origin, so HTTPS is required:

```bash
cd backend && npm run cert
```

This is self-signed: each device accepts a warning once. For a campus
deployment, a certificate from the university's own CA avoids that.

### 4. Build and run

```bash
cd frontend && npm ci && npm run build
cd ../backend && npm ci && npm start
```

The API serves the built app from the same origin, so there is one
address for everything: `https://192.168.1.50:5000`.

Keep it running across reboots with a service manager — `pm2 startup` on
Windows, or a systemd unit on Linux.

### 5. Point the devices at it

Lab PCs (`agent/start-agent.bat`):

```
set SMARTLAB_API=https://192.168.1.50:5000/api
set SMARTLAB_AGENT_KEY=<AGENT_API_KEY>
```

Kiosk terminal — open this **once**, then bookmark the address without
the key:

```
https://192.168.1.50:5000/kiosk?key=<KIOSK_API_KEY>&camera=off&print=rawbt
```

## Option B — Netlify + Render (the chosen deployment)

Two free services, a real certificate, reachable from anywhere.
**Power-on will not work**; everything else will.

The configuration lives in the repository — `render.yaml` and
`frontend/netlify.toml` — so these settings are version-controlled rather
than typed into two dashboards and forgotten.

### Order matters

The two services each need to know the other's address, so deploy the
API first, then the site, then come back and fill in `CORS_ORIGIN`.

### 1. Rotate the secrets first

The Supabase service role key currently in `backend/.env` has been
shared. It grants full database access and bypasses row-level security,
and it is about to be used by a public service. In Supabase: **Settings →
API → Reset service_role key**, and keep the new value to hand.

### 2. Backend on Render

New → Blueprint, point it at the repository. Render reads `render.yaml`
and creates the service. It will prompt for the values the file
deliberately does not contain:

| Variable | Value |
| --- | --- |
| `SUPABASE_URL` | `https://<project>.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | the newly rotated key |
| `CORS_ORIGIN` | leave blank for now |
| `ADMIN_SIGNUP_CODE` | a random string, or leave empty to disable |

`JWT_SECRET`, `AGENT_API_KEY` and `KIOSK_API_KEY` are generated by Render
itself and never leave the dashboard.

When it is live, check it:

```bash
curl https://smartlab-api.onrender.com/api/health
```

### 3. Front end on Netlify

Add the repository as a new site. `frontend/netlify.toml` supplies the
base directory, build command, publish directory and the SPA redirect, so
the only thing to set by hand is:

| Variable | Value |
| --- | --- |
| `VITE_API_URL` | `https://smartlab-api.onrender.com/api` |

**Do not set `VITE_KIOSK_KEY`.** See Security below.

This is read at build time, not at run time, so it must be set *before*
the first build — and changing it later needs a redeploy, not just a
restart.

### 4. Close the loop

Back in Render, set `CORS_ORIGIN` to the Netlify address exactly — scheme
and host, no trailing slash:

```
CORS_ORIGIN=https://smartlab.netlify.app
```

The service restarts. Until this is set, every request from the site is
refused by the browser as a cross-origin violation, and the symptom is a
site that loads but can do nothing.

### 5. Point the devices at it

Kiosk terminal, opened **once** to store its key, then bookmarked without
the key:

```
https://smartlab.netlify.app/kiosk?key=<KIOSK_API_KEY>&camera=off&print=rawbt
```

Lab PCs (`agent/start-agent.bat`):

```
set SMARTLAB_API=https://smartlab-api.onrender.com/api
set SMARTLAB_AGENT_KEY=<AGENT_API_KEY>
```

### Front end on Vercel instead

`frontend/vercel.json` carries the same settings as the Netlify file: the
SPA rewrite, the cache headers and the camera permission the kiosk needs.
In the Vercel dashboard the only thing that is not in the file is:

| Setting | Value |
| --- | --- |
| Root Directory | `frontend` |
| `VITE_API_URL` | `https://smartlab-api.onrender.com/api` |

**Do not set `VITE_KIOSK_KEY`.** See Security below.

Two things that bite:

- **The rewrite is not optional.** Without it `/kiosk` is a 404 on refresh,
  because no such file exists on disk - the router owns that path, not the
  file system. It is the single most common way a working SPA appears
  broken on a static host.
- **`CORS_ORIGIN` on Render has to name the Vercel address**, exactly,
  scheme and host with no trailing slash. Deploying to both Netlify and
  Vercel means both have to be listed, comma separated - the API reads it
  as a list. Until the origin is listed, the site loads and can do nothing,
  which looks like a broken back end rather than a refused origin.

There is no way to deploy *only* the kiosk this way: it is a route in the
single-page app, not a separate build, so the whole front end ships and
the kiosk terminal is simply pointed at `/kiosk`. Nothing else is linked
from it.

### Free-tier note

Render idles a free service after 15 minutes without traffic, so the
first request afterwards takes around 50 seconds while it starts. That is
a poor first impression during a demonstration — open the site a minute
beforehand.

## Security before you deploy

Do these once, before the first public deployment.

- **Rotate the Supabase service role key.** Settings → API → Reset. It
  grants full database access and bypasses row-level security.
- **Set a fresh `JWT_SECRET`.** Changing it signs everyone out, which is
  the intended effect.
- **Set or empty `ADMIN_SIGNUP_CODE`.** Anyone with the code can create an
  administrator. Empty disables self-registration entirely.
- **Leave `VITE_KIOSK_KEY` unset.** A `VITE_` variable is compiled into
  the JavaScript every visitor downloads, so setting it publishes the
  kiosk key — and that key can check bookings in and read cards. Instead
  the kiosk stores its key on the device, put there once through
  `/kiosk?key=…`; the page removes it from the address bar immediately.
- **Never commit `.env` or `certs/`.** Both are in `.gitignore`.

## Database

Run every file in `backend/db/migrations/` in the Supabase SQL editor, in
numerical order, if the deployment is against a fresh project. They are
written to be safe to re-run.

Row-level security is enabled with no permissive policies: the database
refuses anonymous clients outright, and all authorisation lives in
Express, which re-reads the user's role from the database on every
request.

## Checks after deploying

```bash
curl https://<host>/api/health          # {"success":true,...}
curl https://<host>/                    # the landing page HTML
curl https://<host>/api/nope            # a JSON 404, not HTML
```

Then, in a browser: sign in, make a booking, approve it as an
administrator, and check it in at the kiosk. That path crosses every part
of the system.
